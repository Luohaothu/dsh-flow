# 模块设计方案

适用于用户已指明模块的设计编写、修订及接口核验。用户给出的语言、结构、场景和职责划分优先；仓库范围内的选题扫描继续使用原有架构探索流程。

## 工作步骤

1. **固定范围。** 确认本次概念模型所在层次、公开行为和直接责任方。以用户声明的契约评价一致性，宿主内部机制用于判断实现能力；只有本次场景需要时才扩展概念。完成条件是能说明哪些行为在本次保证范围内。
2. **核对现状。** 按仓库 `AGENTS.md` 的资料导航读取当前设计，再定位实现、直接调用方及相关宿主 API。用户说明 PR 已合并时，先更新基线并保留无关改动。分别记录已确认设计、实现事实和待定建议，附足以定位的源码及版本证据。
3. **完成设计。** 用少量概念串起触发场景、调用者、职责及结果。新增 API、状态或关系前，说明现有对象为什么不能完成场景；可由既有配置或对象表达的内容直接复用。源码中的其他异常、重试和关闭分支不因存在就自动纳入范围。用户尚未确定的选择保持为建议。
4. **形成方案。** 新方案默认使用专业中文和下述五部分；修改已有文档沿用其章节。代码标识保留源码名称，架构图、接口及伪代码表达同一组对象和调用关系。
5. **核验交付。** 核验接口闭合、自洽性或可落地性时，读取 [接口核验与逐项讨论](references/interface-review.md)，沿实际调用路径给出结论。用随附脚本验证章节；文档构建、语义审查及运行验证分别报告。HTML 或图示有实质修改时，实际渲染检查可读性。

## 默认结构

新方案只包含以下五个正文一级章节，按此顺序排列；章节内按需使用小标题。

1. **问题分析**：目标模块当前承担什么职责，哪些职责相互依赖，以及这种依赖产生的直接影响。
2. **概念设计/架构设计**：必要概念、职责归属、对象关系和主要交互；架构图放在本节。
3. **接口设计**：接口所属对象、输入、输出和异步操作的完成含义；UML 类图放在本节。
4. **伪代码实现/应用实现**：沿用户给定场景展示主要调用链；伪代码与 UML 时序图放在本节。
5. **实施安排**：按依赖关系列出迁移步骤、形成的结果和与该模块直接相关的验证。

默认结构适用于 Markdown 和 HTML，不增加独立摘要、比较、附录或额外分析章节。用户指定其他结构或逐项讨论时，按实际交付形式组织，不为套用模板重排已有设计稿。

## 章节校验

Markdown 用 `##` 表示五个正文一级章节。HTML 的 `main` 内用 `h2` 表示对应章节。页面标题、导航及章节内的 `h3` 不算额外正文一级章节。

在仓库根目录运行：

```sh
python3 .agents/skills/module-design/scripts/check_sections.py <方案文件>
```

用户指定其他章节时，以实际标题覆盖默认列表：

```sh
python3 .agents/skills/module-design/scripts/check_sections.py <方案文件> --sections "章节一" "章节二"
```

修改检查脚本时，运行其已有测试：

```sh
python3 -B -m unittest discover -s .agents/skills/module-design/scripts -p 'test_*.py'
```

脚本只验证章节结构。接口语义、职责及跨图表一致性由审查判断；站点构建通过不等于浏览器中的图示已渲染，更不代表运行时契约已验证。
