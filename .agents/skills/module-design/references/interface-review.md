# 接口核验与逐项讨论

用于已有设计的闭合性、自洽性和可落地性核验，以及用户明确要求的逐项设计讨论。

## 沿调用路径核验

1. 从用户已声明的场景出发，列出触发者、调用对象、输入来源、返回值的消费者及资源责任方。每个跨模块步骤都应能落到已有或本次明确设计的接口。
2. 对照方法签名与文字承诺，核对返回值和事件是否足以推进下一步。异步完成要区分“已接管请求”“逻辑状态已改变”“执行或清理已完成”；对象复制、身份和生命周期也应一致。
3. 查看宿主实际依赖版本的公开 API 和直接参考实现。向用户讨论问题时，如有对应实现，简要说明它怎样做、能支撑什么、有什么限制；没有直接对应实现时如实说明。把宿主机制映射到既定概念，保留层次边界。
4. 仅对用户明确提出的异常和边缘情况，沿对应路径核验状态维护、对象可用性和后续事件影响。不要以接口完整性或实现可行性为由自行扩展这些情况。

缺口应表达为“哪个场景在什么调用边界无法继续，以及缺少什么信息或行为”。缺少一个内部方法名、游标或锁方案，本身不构成公开契约缺口。

## 新增概念的依据

新增接口、状态或管理角色前，先回答：何时触发、谁有权触发、现有对象为何不足。无法给出实际场景时，先保留现有模型。

优先复用已有对象及配置字段。逻辑状态与后端执行事实分别建模；宿主内部的附加能力不会自动变成所有后端都必须实现的 Flow 概念。后端能力不足时，按已确认契约报告限制，不自行放宽承诺。

## 逐项讨论

仅在用户要求“一个一个讨论”或约定逐项提交时采用以下流程；其他已授权任务连续推进。

1. 提出当前一项外部行为或职责选择，给出参考实现和最小建议。
2. 用户确认后，只落实该项及其必需的契约衔接，完成相应检查。
3. 按用户约定询问是否进入下一项；若约定批准后提交，则获准后先提交本项，再讨论下一项。最后一项说明已收口，并按约定确认提交。

涉及范围、公开行为或责任归属的选择交给用户；已确认规则下的内部实现选择由实现者处理。复盘和批量文档整理不因曾采用逐项讨论而自动继承每项审批流程。提交与推送分别遵循当前授权范围。

## 结论与完成条件

已声明场景都有明确调用路径、输入输出和职责没有冲突、宿主具有实现途径后，可以建议进入实现；不要继续扩张无具体场景的问题清单。仍有缺口时，明确它是否阻止某个场景落地，并给出最小补充。

结论分别说明：

- **模型自洽**：同一概念、状态及职责没有相互冲突的承诺。
- **接口闭合**：跨模块调用有足够的输入、结果和完成含义。
- **实现可行**：宿主公开能力可以承载已声明行为，限制已说明。
- **运行证据**：哪些实现及场景实际运行过；文档通过审查不代表它们已经实现。

格式和构建错误交给现有脚本；语义和责任边界交给审查。读取原始日志或源码时先定位相关范围，输出必要片段，避免重复展开整份会话或文档。
