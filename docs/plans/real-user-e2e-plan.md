# dsh-flow 真实用户自主协作端到端测试方案

状态：用户已授权执行。按测试批次保存实际证据并分别提交 PR，进度见[执行记录](../validation/real-user/README.md)。

## 1. 测试目标与通过标准

以[设计文档](../design/design.md)为行为和界面的验收依据，检验用户只表达需求时，Agent 能否自主理解目标、组织团队、拆解工作、运行协作、处理事件、验收结果并向用户交付。当前核对的实现基线为 `main@0a92333`；执行时冻结实际提交、DSH 版本、SDK 适配和插件包哈希。

`/agent-team` 是面向用户的 **skill**，由普通主会话 Agent 接收调用和需求。主线首条输入采用 `/agent-team <自然业务需求>`。技能加载、团队选择或创建、顶层作业派发、根的组织决策及最终验收共同构成被测能力；宿主中的斜杠输入展示只是技能的使用入口。

### 用户输入与测试者职责

主线输入只给业务目标、正常材料和必要的业务约束，不指定角色、人数、模式ID、工具、schema、作业关系、消息优先级或事件处理步骤。模式选择、团队规模、成员复用、工作交接、等待、重试和收尾由 Agent 判断。普通项目材料不夹带编排答案、测试编号、工具调用指引或隐藏验收脚本；`agent-team`、`team-strategy`、模式管理指引及相关提示词是被测系统的一部分，可通过第7节的版本化实验改进。每轮开始前固定版本并通过正常安装加载；运行中不临场改写引导来救援当前案例。

测试者按预先准备的业务事实回答必要澄清，例如目标平台、交付范围或哪份材料更新；不知道的事实就回答不知道。Agent 把人数、模式或工具选择推回用户时，记录该行为，不提供编排答案。正常业务澄清不算人工救援；提示该调用什么工具、读哪份作业、如何恢复执行后得到的结果，单列为“人工干预后完成”，不能计入自主通过。

跟进消息只表达业务变化、追加需求、停止或继续意图。关闭窗口、重连、重启和查看界面是正常用户操作，按用例触发；其时间线留证。观察器只读取现有会话、日志、事件、快照和产物，不替 Agent 发消息、派作业、创建成员、唤醒会话或注入预定工具序列。瞬态未自然发生时记未观察，不通过挂起业务或伪造事件制造覆盖。

### 自主能力的可观察判据

| 环节 | 验收问题与证据 |
| --- | --- |
| 理解需求 | 是否识别业务目标和关键约束，读取实际材料，发现影响交付的信息缺口，并自行形成合适的任务要求与结果结构？ |
| 组织与拆解 | 是否真正通过该skill选择或创建Flow团队、派发顶层作业？复杂工作是否按业务依赖安排责任与交接，组织规模是否合理，是否考虑已有成员与可用模式？ |
| 推进执行 | 是否实际开展工作、取得产物，依据进展继续派发、读取结果或调整安排，而不是只描述计划或建出空树？ |
| 事件处理 | 在真实完成、失败、用户改动和中断发生后，能否自行关联任务、判断下一步并恢复推进？没有事件时不臆测这一能力已验证。 |
| 结果验收 | 主会话是否读回真实交付，核对用户需求与证据；有质量问题时能否继续修正或明确报告未完成？schema校验成功不等于业务结果正确。 |
| 交付与收尾 | 是否向用户提供可使用且可核验的成果，区分已完成、未解决和待用户决定事项，保持任务与团队生命周期正确？ |

判断依据是可见操作和产物，不要求输出内部思维过程。简单任务可以由团队根自己完成，不强制生成子成员；主会话绕过团队独自完成任务，则业务结果可正确，但skill自主协作不通过。对于复杂任务，不把某一棵预定树或某个模板作为唯一答案，而是检查任务是否被充分处理、责任与依赖是否落实、返工及资源使用是否合理。

每次运行独立记录 **业务结果、自主协作、界面体验** 三项结论，同时更新模式、特色能力和规模覆盖矩阵。一次合理替代路线可以取得业务和自主协作通过，但不能关闭尚未覆盖的目标；需继续调整任务复杂度和通用skill引导并重新测试，直至取得真实证据。已有证据表明协作不足造成遗漏、冲突未处理或停滞时，按实际失败归因。只有口头宣称、创建空组织或辅助定向调用，均不能填入自主覆盖的通过单元。

## 2. 干净环境与模型接入

### 实例隔离与安装

采用独立实验目录、空 `DSH_HOME`、空 profile、独立 Flow 状态目录及测试工作区。使用仓库锁定的 Node、pnpm、DSH `0.2.0-rc.2` 和八项 SDK 适配，冻结依赖安装后重新构建、打包，通过官方插件管理器安装 Flow。具体入口依据[包安装说明](../../packages/dsh-flow/README.md#在锁定宿主中安装)。

安装验收记录 CLI、profile 与 Flow 的 SDK 解析位置、适配文件和产品包身份，确认没有借用旧 P7 profile、旧会话、日常 DSH home 或旧 Flow 状态。只安装正式 Flow 插件及宿主正常所需组件。测试材料放入专用工作区，答案和检查器放在模型不可访问的目录。

执行入口分为：

| 环境 | 用途 |
| --- | --- |
| DSH Web 宿主 | 全部自主协作主场景，从实际主会话调用skill并输入需求；同时验证宿主原生插件界面。 |
| 同一宿主的独立 Flow Web | 与该宿主的运行、实例、作业和结果对照；核验共享画布和详情。 |
| 匹配版本的真实 Desktop | 使用新的 Desktop profile 和同一产品包，重跑基础、持续工作、复杂协作、自定义模式与中断场景，核验原生界面。 |

Desktop 必须加载匹配的 SDK 和正式完整插件包。普通 Flow tarball 不会适配任意已安装桌面版本。各宿主进程分别记录身份；仅在同一后端内比较 Native 与独立 Web 的同一运行。

每组独立场景从干净会话和工作区副本开始。复用、多作业、多会话和冷恢复用例明确保留其所需状态。前一场景遗留的团队或配置不得意外成为下一场景的前提。

### 模型接入与公开范围

具体测试服务、供应商、套餐、模型名称与ID、接口地址、账号、凭据位置、接入参数和实际额度仅保存在本地私有执行记录中，不写入公开方案、Issue、PR、提交说明、日志、截图或附件。公开材料统一使用“测试模型A/B”等匿名标识，也不得通过链接、文件名或Logo间接透露实际配置。

接入时保留原凭据文件，通过专用实例的正式凭据服务提供配置。先核对账号能力和模型ID，再通过普通主会话执行一个自然需求，核对实际工具使用和回答接续。主线固定显式模型；其他模型用于相同最小场景、代码任务、独立复核及跨模型协作。不可用项记为接入阻断，不静默替换后仍以原模型报通过。

推理、采样、输出长度和工具协议按实际能力校准，配置快照留在本地。图片场景只在模型支持相应输入时执行。原始证据用于本地核验，公开报告仅提供脱敏后的测试方法和结果。

## 3. 测试材料与独立答案

准备离线项目 `release-lab`，让输入保持简短、业务本身具有足够复杂度。每个案例的目录只含正常用户会提供的材料，不把理想组织结构和工具顺序写入 README。

| 材料 | 业务内容 | 测试者持有的独立判据 |
| --- | --- | --- |
| 订单与退款数据 | CSV、业务口径说明、同名但不同内容的两套账目 | 重复记录、错误金额、退款与零值边界；独立脚本计算的逐条问题及汇总 |
| 小型代码项目 | 可运行项目、普通测试、真实缺陷表现和待实现需求 | 隐藏验收验证正确行为、文件差异及运行结果；不规定具体代码写法 |
| 发布材料 | 需求、实现说明、测试报告、业务风险、审批记录 | 6处可定位矛盾、2处证据缺口、2项待决定事项；上线建议必须与证据一致 |
| 跨模块材料 | 模块接口、字段口径和相互依赖，局部结论正确但合并后存在冲突 | 覆盖清单、依赖关系和全局矛盾；判断是否真正完成整合 |
| 附件与长文本 | 中文长文件名、CSV/JSON/Markdown，支持时含图片 | 材料身份、内容与引用位置；没有问题的数据保留合法零值与空结果 |
| 用户已有模式包 | 正常业务说明、角色职责、适用条件和可选参数 | 模式是否被发现、是否适用、实际使用是否符合其定义；不把选择答案塞入需求 |
| 规模材料 | 小档1个模块/5份材料，中档6个模块/30份材料，大档12个模块/100份材料 | 全量事实与依赖答案；数量是测试材料档位，不是要求创建的人数 |

答案、隐藏检查器和运行账本位于模型不可访问的独立目录。每次记录材料哈希、实际产物及独立验收结果。所有关键业务事实都应能够由用户材料或正常澄清获得；隐藏的是评分答案，不隐藏完成任务所需的事实。

用户模拟器另有一份事先固定的业务答复表，只回答 Agent 实际提出的问题。测试者不因看见团队走错方向就主动补充答案。代码检查失败、材料矛盾和缺失批准作为真实问题存在，由 Agent 发现和处理；不在验收时倒推应当预先指定哪些角色。

## 4. 自然需求主线场景

以下 **20个基础场景**与第5节的模式任务族共同构成主线；每个场景的“用户输入”列就是送入主会话的内容；“环境或使用事件”和“验收重点”仅供测试者执行、观察和评分，不作为提示词。跟进句子在同一主会话中发送，除跨会话或重启场景外，不额外创建会话或清空所需状态。

| 编号 | 用户输入 | 环境或使用事件 | 验收重点 |
| --- | --- | --- | --- |
| N01 数据查错 | `/agent-team 帮我检查这份订单表有没有问题。` | 全新实例和主会话，提供订单表与日常口径说明。 | skill实际加载并启动团队工作；发现可证实的问题，读取实际交付后回复。允许根自行完成，不要求固定人数。 |
| N02 修复缺陷 | `/agent-team 修好这个项目的金额计算问题。` | 提供缺陷项目和用户报告。 | 自主定位、修改、验证；隐藏行为检查通过，交付与文件实际变化一致。用户不指定实现者或复核者。 |
| N03 完成小功能 | `/agent-team 给这个工具加上退款汇总功能。` | 普通项目已有订单汇总，需求含正常业务口径。 | 自行形成实现及验收安排，完成可运行交付；处理零值、重复及退款边界，不能只给方案。 |
| N04 发布判断 | `/agent-team 看看这个版本能不能上线。` | 提供完整发布材料。 | 综合事实、测试证据、矛盾和审批状态，给出有依据的结论；不同材料之间不能只拼接摘要。 |
| N05 模糊目标 | `/agent-team 帮我把这个项目改好。` | 业务答复表有目标用户和交付范围，尚未在首条输入给出。 | 自主识别关键歧义并获得必要业务信息，不擅自无限扩展，也不要求用户设计团队。随后按澄清目标交付。 |
| N06 连续相关任务 | N01完成后：`/agent-team 这份退款表也帮我检查一下。` | 同一主会话提供另一份材料。 | 自主判断已有团队是否适用；适用时能复用历史能力，原结果仍可读，新任务结果不混淆。无需用户说“复用成员”。 |
| N07 执行中追加任务 | N02进行中：`/agent-team 另外把使用说明也补齐。` | 在真实执行期间追加相关需求。 | 自主判断依赖与优先关系，持续跟踪两项要求，交付覆盖代码与文档；不要求两份任务必须由同一成员或并行执行。 |
| N08 多主会话隔离 | 两个主会话分别输入：`/agent-team 帮我核对这批订单。` | 提供名称相同、内容不同的数据集，交错查看两个会话。 | 团队、材料、通知与结果归属正确；用户无需给出Run或作业ID。 |
| N09 跨模块一致性 | `/agent-team 检查这些模块合起来能不能正常发布。` | 各模块材料存在接口及统计口径依赖，局部正确不保证整体正确。 | 自主安排整合和必要交流，发现跨模块矛盾，形成一致结论。观察是否自然选择群聊或共享证据，不在输入中要求建群。 |
| N10 不完整证据 | `/agent-team 这些材料够不够支持上线？` | 部分证据缺失、两项批准未完成；缺失事实确实未知。 | 识别并保留不确定性和待决定项，不编造批准；能继续完成已具备证据的部分并说明阻断。 |
| N11 执行失败处理 | `/agent-team 把这个项目跑起来。` | 普通构建/测试因真实代码缺陷失败，工具如实返回错误。 | 自主读取失败信息、定位并修正、再次验证；不能把命令已执行或任务已提交当成成功。若无法修复，业务结果记失败；准确说明原因不能代替修复通过。 |
| N12 中途改变范围 | 先输入 `/agent-team 给工具加上退款汇总和导出功能。`，进行中：“这次先不做导出功能，退款汇总做好就行。” | 导出属于原始业务范围；仅在相关工作确实尚未结束时触发变化。 | 自主关联范围变化、调整或停止无用工作；保留仍需完成的部分。不能让测试者指定取消哪份作业。 |
| N13 暂停与继续 | 执行中：“先停一下，告诉我目前做到了哪一步。”之后：`/agent-team 接着完成刚才的事情。` | 先按N03发起任务，工作实际开始后正常暂停及继续。 | 根据意图停止或恢复工作、如实汇报进度；不擅自丢弃成果。由Agent决定作业和成员处置，不要求用户选择停止信号。 |
| N14 完成事件接续 | N04进行中：“顺便解释一下这份说明里的术语。” | 用户在等待期间正常提问，团队可能在主会话忙碌或空闲时完成。 | 主会话能处理完成通知并读回对应成果，不靠用户追问“结果呢”才完成交付；忙碌/空闲分支按实际发生分别留证。 |
| N15 页面中断 | `/agent-team 检查这次发布材料。` | 开始后关闭测试页面，再回到同一会话；后端保持运行。 | Agent继续工作，重连后的页面与真实状态一致，结果不丢失；不向Agent发送补偿事件或重新派发原任务。 |
| N16 宿主重启后继续 | `/agent-team 接着完成上次没做完的事情。` | 先用N09需求发起工作；有已保存的成果且仍有工作未完时正常退出并重启专用宿主，打开原主会话。 | 自主辨认历史与当前运行，查找实际成果并组织继续工作；不把失效句柄当作有效状态。无需用户指定恢复哪个实例或如何关联作业。 |
| N17 已有自定义pattern | `/agent-team 看看这次发布能不能上线。` | 事先通过正常设置导入用户发布审查模式；也保留正常内置候选。 | 自主发现适用模式并判断是否采用，实际采用时验证用户定义的职责、参数和关系。合理另选路线不强行判错，但自定义pattern机制不能记通过。 |
| N18 不适用的自定义pattern | `/agent-team 修好这个项目的金额计算问题。` | 目录中额外放入仅适用于盘点材料的用户模式。 | 自主判断适用范围，不能仅因“用户模式”优先就套用无关组织；实际任务仍正确完成。 |
| N19 用户建立可复用模式 | `/agent-team 把我们的发布审查习惯做成以后能直接使用的团队模板。` 后续：`/agent-team 按我们的发布规范检查这一版材料。` | 输入正常组织惯例；模式交付后，用户按交付说明完成必要的普通导入设置，再在新主会话使用。 | Agent自行设计角色、结构和参数，交付有效模式及可操作说明；下一次能自行发现和使用。若只生成当前Run内定义，不得宣称已永久可用；语法修正不得由测试者代做。 |
| N20 工作量递增 | 各档均输入：`/agent-team 检查这个版本所有模块能不能上线，给我完整的问题清单和建议。` | 小/中/大三档分别用全新环境副本和第3节对应材料。 | 观察Agent如何选择组织、规模、协作与验收；全量检查独立答案、覆盖和整合质量。记录真实峰值人数、有效工作成员数和依赖处理；不向Agent指定人数，测试者按第5节档位验收。 |

N12–N16的事件依据预先写定的可观察条件触发，例如目标工作已开始且尚未完成，不依据“缺某个工具调用”临时补提示。事件早于或晚于目标状态时，保留原次结果并将该分支记未触发。正常重跑仍使用相同业务目标，下轮可依据第7节调整业务表达和复杂度，但不把人数、模式ID或工具步骤写入用户输入。

N20的三档允许形成不同团队拓扑。小团队完成大材料集，不因人数少直接判失败；大团队也不因节点多直接判通过。逐项核对实际业务覆盖、产物整合、成员职责和有效工作，报告组织变化与实际成本。若没有形成目标规模或群聊，该目标保持未完成，继续调整独立工作量、跨组依赖、上下文负荷及skill策略。辅助诊断帮助定位问题，但不补足主线自主覆盖。具体规模目标与判据见第5节。

## 5. 模式、特色能力与规模覆盖

### 覆盖目标与任务构造

本轮将[设计目录](../design/design.md#团队模式与作业)中的14个模板纳入目标，先推进常用分工、复核、共享与分层协作，再推进组合、搜索和演化。矩阵内的模板ID和目标只对测试者可见；用户输入仍是 `/agent-team` 加业务需求。一个任务族可以有多个难度和材料变体，也可能在实际执行中同时覆盖多个目标。

| 任务族 / 目标模板 | 自然需求示例 | 用业务复杂度创造协作需要 | skill可迭代的通用判断重点 |
| --- | --- | --- | --- |
| M01 `builtin/independent-vote` | `/agent-team 核对这批结算结果，给我可靠的结论。` | 多种等价表达、易混口径、可客观核对的争议项；错误影响较高。 | 何时独立初答有助于降低共同误判，如何保留证据而不是只数赞成票。 |
| M02 `builtin/heterogeneous-ensemble` | `/agent-team 核对这些不同格式的资料，确认结论有没有遗漏。` | 合法可访问的文本、图表、代码及多语言资料，存在能力互补需求；正常配置提供可选模型。 | 根据真实能力、成本和限制选择互补成员，核对实际贡献与合成依据，不把换标签当异构。 |
| M03 `builtin/debate` | `/agent-team 这几个改造方案该怎么选？` | 可证伪的不同主张、约束冲突和证据缺口，最终需可解释取舍。 | 何时保留竞争立场、交换论据、修正主张并结束讨论，避免无依据达成一致。 |
| M04 `builtin/expert-router` | `/agent-team 看看这个项目上线前还有哪些风险。` | 数据、代码、安全边界、性能和运维材料有专业差异及部分关联。 | 按问题选择相关专长和核验责任，避免每个问题都让所有成员重做。 |
| M05 `builtin/pipeline` | `/agent-team 把这些需求做成一个可以使用的小工具。` | 需求澄清、实现、验证和交付有真实依赖，前序变更会影响后序。 | 识别前置产物和验收门槛，基于实际结果交接与返工，不机械按固定轮数推进。 |
| M06 `builtin/hierarchical` | `/agent-team 全面检查这个版本的各个业务模块能否上线。` | 多个领域各自包含若干独立事项，存在域内复杂性和跨域依赖；根直接管理的负荷逐步增大。 | 何时划分子领域、设置管理层、把继续拆分交给子团队，并核对跨层交付。 |
| M07 `builtin/mixture-of-agents` | `/agent-team 把这些分散的建议整理成一套可实施的改进方案。` | 多份互补但局部不完整的建议，需要比较、提炼和二次整合。 | 识别独立提议到提炼再到综合的信息层次，传递完整结果与失败信息；不把信息层误当管理树层级。 |
| M08 `builtin/generate-review-revise` | `/agent-team 把这份交付材料改到可以验收的程度。` | 现有成果有可定位缺陷，修订可能引入新的关联问题。 | 形成、独立审查、验证和修订之间依据证据循环，定义何时足够而不无限润色。 |
| M09 `builtin/tool-specialists` | `/agent-team 解决报表结果、程序输出和使用说明对不上的问题。` | 多类真实产物需分别读取和验证，正常安装的预设/技能提供不同能力。 | 依据实际可用工具能力和权限分工，交接真实产物而不只转述。 |
| M10 `builtin/search-swarm` | `/agent-team 查清这个间歇性错误是怎么发生的，并修好它。` | 多个可疑子系统、分散日志与多条初始线索，线索出现后可缩小范围。 | 多线探索、局部共享线索和证据驱动的收束；及时停止失去价值的搜索。 |
| M11 `builtin/workflow-search` | `/agent-team 为以后反复开展这类审查找个更可靠的协作办法，先用样例试一试。` | 周期性业务、不同失败类型与可比较样例，现有做法没有同时满足质量与成本要求。 | 根据真实试运行比较组织方案，候选必须能够创建和执行，不能只比较文案。 |
| M12 `builtin/sparse-routing` | `/agent-team 把这些异常处理好，避免遗漏和重复处理。` | 大量局部问题分别影响不同模块，少数问题需要跨域传递；全量广播会产生明显噪声。 | 根据受影响范围定向传递，必要时建立局部协作，验证相关方收到而无关方不被淹没。 |
| M13 `builtin/shared-review` | `/agent-team 核实这些互相矛盾的发布材料，给我一个有依据的结论。` | 不同材料掌握互补事实，口径更新会影响多人结论，必须追溯证据及更正。 | 判断何时需要多人共同讨论和共享证据，何时用正式作业交付；保证分歧和未决事项不丢失。 |
| M14 `builtin/tournament-evolution` | `/agent-team 在这些约束下改进排程，给我效果更好的可执行方案。` | 候选可按公开业务规则计算可行性与目标值，初始方案各有长短，需要继续改良和保留不同方向。 | 保留候选身份，依据比较结果选择、组合或改良，并按收益停止；不用模型编造分数。 |

材料复杂度按独立工作项、依赖密度、证据冲突、专业异质性、上下文长度、更新频率和错误代价逐项调节。增加真实且可验的业务负荷，不靠重复堆字数或添加“必须采用某模式”暗号。M02/M09先确认Agent能够通过正常产品能力目录获知可选能力；若缺少发现入口，记录并解决产品或配置缺口，不能由测试者临场塞模型ID或工具白名单补成自主成功。

每个M目标分别记录两列：**协作形式的实际执行**与**对应模板的实际采用**。相似拓扑本身不能证明任一列。协作形式要求下表的真实行为；模板业务验证还要求实际选择/应用、展开关系、有效工作及交付记录。只创建结构或只应用模板均不能通过。

| 任务族 | 对应协作必须具有的过程证据 |
| --- | --- |
| M01 | 在互读同伴答案前形成独立初答，真实归一化、计票和证据核验；失败答案不能当有效票。 |
| M02 | 至少两种实际模型各自产生有效结果，汇总使用真实来源、失败影响和合成依据；身份只在私有证据中记录。 |
| M03 | 初始主张、具体论据交换、质疑与回应，以及基于证据的评审取舍。 |
| M04 | 子问题实际送到相关专长成员，按缺口补充并整合，避免无差别重复全题。 |
| M05 | 后续工作实际读取前序产物，依据结果推进或返工，最后交付可验证。 |
| M06 | 多层直属作业、子团队实际管理与交付、跨组协调和结果整合。 |
| M07 | 上游完整结果及已发生的失败进入提炼和再整合；信息层次有真实交接，管理树可以是平的。 |
| M08 | 独立审查产生有依据的反馈，作者据此实质修订，最新产物再验收；初稿正确但无返工只能说明该轮业务通过。 |
| M09 | 成员实际使用对应能力，交接可读取的工具产物，权限真实生效并完成整体验证。 |
| M10 | 多线搜索和共享线索，先到证据改变后续搜索方向，采纳结论经实际复现或独立检查支持。 |
| M11 | 候选定义、注册、创建、样例作业和基于真实结果的比较；只生成模板或口述比较不算。 |
| M12 | 按相关性选择证据和接收者，接收方实际读取并处理；无关方未收到全量广播，结果形成闭环。 |
| M13 | 实际群交流、共享证据的读取与更正，以及由此产生的核验和审查结论。 |
| M14 | 候选实测比较、选择及基于真实父候选的改良/组合，来源关系和目标值可追溯；单轮排名不足以覆盖演化。 |

这些判据与独立业务验收同时成立才计入覆盖；不能凭角色名称、树形或最终自述通过。

### 特色能力的必达证据

| 编号 / 目标 | 自然需求与任务条件 | 必须观察到的实际行为 |
| --- | --- | --- |
| G01 群聊与共享黑板 | M06/M13中，多份材料的更新会同时影响相关方，存在需要共同核对的争议。用户仍只要求完成业务。 | Agent自行组织群聊，相关成员真实交换证据并影响后续判断；共享黑板有有效新增或更正。只有预置空群不算通过，黑板写入也不能当消息送达。 |
| G02 对话与配置继承（fork） | 已完成一轮分析后，用户补充“原方案先保留，再看看新的约束下有没有更合适的办法”。准备足够已积累的上下文，使重新推导有明显代价。 | Agent判断保留基线并派生探索；实际fork获得正确历史与Profile，形成独立后续轨迹；捕获的既有历史不被改写，允许来源随后正常追加，旧作业不被隐式继承。 |
| G03 多来源上下文合并（herb） | 同一业务的两条调查积累互补历史及未解分歧，用户要求“结合目前掌握的情况给出后续方案”。 | Agent自主采用herb并继续工作；两份来源总结与一次合并逻辑操作真实发生，六节结构及未决冲突、批准事项保留；捕获的来源记录不被改写，总结不写回来源，允许来源随后正常追加；新子节点的后续工作使用实际合并上下文，传输重试另计。 |
| G04 子团队与嵌套组织 | M06各领域内部仍需不同工作，随后又加入一个复杂业务模块。 | 既覆盖模式嵌套产生的实际子树，也覆盖成员自行继续扩充直属子团队；父子管理关系、作业关联、局部群及跨组整合正确，不能用根下平铺成员替代。 |
| G05 默认值、角色及派生配置继承 | 用户正常配置角色能力与权限，任务中产生新成员；后续普通配置变化后再启动新任务。 | 记录运行默认快照、角色及显式覆盖来源；旧Run后续创建成员仍读旧快照，新Run才读取更新默认。既有Profile不被改写，fork/herb复制母版Profile而不重解析新默认；新任务不等于新Run，权限不越父级初始上界。 |
| G06 团队事件处理 | N07/N11–N16及M08中，完成、失败、审查退回、补充信息、范围变化、等待与重启真实发生。 | 逐类核对事件与Agent下一步动作，实际读回/验收、修正或重派、停止无用工作、恢复推进；只收到通知或口头回应不算处理完成。 |
| G07 运行中职责调整 | 已有复杂任务的业务归属变化，例如某模块并入另一领域，且旧任务有未完部分。 | Agent能自主调整协作归属；需有实际transfer证据才能覆盖转移，原Profile和既有作业谱系不被改写，后续委派符合新父子关系。 |

G02/G03要求调用与上下文证据；重新创建成员后手工附一段摘要不能冒充fork或herb。G01分别登记局部群交流、跨组转交及共享证据读取/更正，G04分别登记静态嵌套与运行中扩充，不能用其中一个代替全部。“继承”分别检查对话/Profile派生和默认配置来源。

G06逐项登记：主会话空闲时的完成通知及读回、主会话忙碌时的接续；工具执行失败后的处理；正式作业failed通知及父级后续安排；审查反馈后的修订复验；补充信息与范围变更；取消后的收尾；主动wait匹配及timeout后的判断；重启后的历史辨认和继续。命令退出失败、作业结果里写“失败”和正式作业failed不是同一事件，等待匹配也不能替代超时。

事件通过真实工作和正常使用条件产生，例如用正常产品停止操作中断正在承接任务的成员，核对真实failed通知后Agent的自主处置。测试者只触发预定的使用事件，不告诉Agent应如何恢复，不伪造通知或返回结果。等待目标可通过实际较长的协作和正常分批材料到达创造条件，不用门闩强行卡住执行。若某子项未发生，下一轮调整业务时序、复杂度或通用等待/处理策略；辅助注入成功不能填入该子项。

### 规模覆盖

建议本轮覆盖单根基线、2–5人、6–12人、13–30人，以及至少50名有效成员的大团队；这些是测试档位，不是产品上限，也不写入用户需求。通过业务分域、域内独立事项、交叉核验与上下文负荷调节任务，配合skill中可泛化的分工和管理负荷策略，让Agent自己决定组织规模。

人数包含Flow根，不含树外主会话。规模以同一Run、同一组织快照中可追溯到本次业务实质贡献的成员为依据；记录同时在队的成员峰值、实际工作成员数、角色职责、模型/工具执行和有用交付，空闲空壳另列。不能累加不同Run或多轮重复凑人数，也不能用建出50个空节点完成大规模验收。人数够但任务质量、协作或界面不可用，同样不通过。

若Agent始终用较小团队完成业务，保留该次正确结果，继续设计更有领域跨度和独立责任的任务并验证通用策略。目标规模未实际达到时，本组覆盖仍未完成；不能改成“只测试了现有规模”后宣布整套测试完成。固定人数的X03只用于排查容量和界面问题，不能代替这里的自主规模证据。

### 自定义模式的自主性判定

用户可以事先拥有团队pattern，或者通过N19要求Agent把业务惯例整理为可复用方案。之后使用时仍只提交 `/agent-team` 和业务需求。N17检验发现与采用，N18检验适用性判断，N19检验生成、交付与再次使用；三者不通过在提示中指定模板ID来取得通过。

模式并非唯一正确解。记录Agent实际见到的候选及其可见决策证据：未发现可用模式、选择不合适模式、合理采用另一方案、实际使用用户模式，分别报告。若合理替代方案成立但用户模式从未被采用，该案例可有正确交付，用户模式适配能力仍缺少实测证据，需要继续任务/skill迭代完成该目标。N19只按业务惯例约束有效模式，不要求生成与N17夹具相同的YAML。

N17预置的用户模式包采用以下结构，文件通过正常设置加载。它属于用户已有环境，不作为本轮用户输入，也不预先替本轮任务派发任何作业：

```text
user-patterns-v1/release-review/
  pattern.yaml
  guidance.md
  roles/author.md
  roles/reviewer.md
```

`pattern.yaml` 内容：

```yaml
apiVersion: v1
id: user/release-review-v1
description: 作者整理发布材料，独立复核者交换证据并核验结论。
whenToUse: 发布结论需要独立审查，且需要保留未决问题。
parameters:
  reviewers:
    type: integer
    description: 独立复核者数量
    default: 2
roles:
  author:
    instructions: { file: roles/author.md }
    permission: workspace-write
  reviewer:
    instructions: { file: roles/reviewer.md }
    permission: read-only
root:
  instructions: { file: guidance.md }
  author:
    role: author
  reviewers:
    role: reviewer
    count: "{{ reviewers }}"
groups:
  - key: release-discussion
    members:
      - root
      - root/author/0
      - root/reviewers/*
```

`guidance.md` 表达长期业务惯例：结论有证据、关键判断独立核对、未批准事项保持未批准；作者整理报告，复核者核对原材料。是否交流、何时交接以及如何推进由Agent结合当前任务判断。文件不包含测试答案、固定工具序列或按测试要求强制使用群聊的指令。

预置根权限允许作者在工作区内写入；权限边界不超出正常授权。参数由Agent在采用该模式时选择，测试者按真实选择核对展开结果，不向其透露期望人数。N18另外预置不适用模式，N19完全使用Agent实际生成的模式。

辅助模式测试覆盖包目录、嵌套引用、参数边界、无效定义及目录快照。配置变更使用真实保存；旧运行与新运行分别核对。依据：[模板契约](../design/design.md#模板定义与管理指引)、[当前目录加载器](../../packages/dsh-flow/src/patterns/catalog.ts)、[配置应用](../../packages/dsh-flow/src/plugin.ts)。

### 辅助白盒与容量检查

下列检查用于定位原因或补充机制及界面覆盖，独立建档，不能计入主线的自主通过率，也不能在主线未完成时替代主线结论。

| 编号 | 辅助范围 | 证据边界 |
| --- | --- | --- |
| X01 模式与配置边界 | 固定参数、0人数分支、嵌套use、非法引用、目录版本快照、角色配置与权限的精确边界 | 允许精确输入参数，验证编译、应用和错误提示；不证明Agent会自行选择模式。 |
| X02 通信与派生机制 | 群聊、黑板、优先级、wait、fork、herb、transfer的未覆盖分支 | 需要定向触发时使用独立诊断用例；验证实际契约，保留失败，不能当作自然用户会话。 |
| X03 固定规模与容量 | 8/20/50节点真实工作、多个Run共享容量 | 用正式接口构造明确规模，不用伪造快照；核对实际工作与界面。只证明对应容量及呈现，不证明Agent能自主组织该规模。 |
| X04 生命周期边界 | 精确停止范围、取消树、条件性retry、插件卸载重装 | 正常产品入口和真实实例留证；没有满足前置条件时记未触发，不假造运行失败。 |
| X05 设置与展示边界 | 参数非法值、两窗口保存冲突、缺失用量、固定复杂群框等 | 验证功能和视觉状态；与主线自然出现的状态分别标明来源。 |

辅助检查可在主线探索中用于定位问题，在约定预算中单列。每次运行的来源在开始前标明为主线、辅助或人工干预后复现，不因结果好坏改标签。既有受控集成记录只作参考。自然运行中若已取得充分证据，可复用同一份只读记录进行契约核对，无需为了补机制计数重复制造运行。

## 6. 前端功能、外观与交互验收

前端检查首先绑定主线自主生成的真实组织和数据，辅助造出的状态明确标注来源；除稳定截图外，动态过程录制短视频。视觉验收包括设计尺寸、状态含义和阅读质量，不以“页面能打开”或截图像素相似替代完整判断。

### 页面和状态覆盖

| 编号 | 页面/组件 | 具体检查 |
| --- | --- | --- |
| U01 安装与空态 | 插件列表/详情、用户skill的斜杠输入展示、全局入口、会话页签、顶部团队下拉 | 插件和技能入口只出现一次；`/agent-team`以用户skill呈现，输入需求后实际加载正式skill内容，不能只有文本回显；空态示例不要求用户提供组织细节，运行数量与实际一致。 |
| U02 全局与会话导航 | 全局“智能体”、当前会话页签、顶部成员行/独立箭头、返回发起会话 | 运行来源正确；主行定位与观察箭头行为不同；切换会话恢复各自选择、折叠和视点；关闭菜单返回焦点。 |
| U03 团队画布与列表 | 自主产生的各规模树、子团队、继承关系、长名称和跨分支群；X03另验固定规模边界 | 卡片、连线和群框贴合实际几何；缩放、平移、适应视口、折叠/展开可操作；隐藏后代计数准确。业务结构用实际入口检查，不假定存在设计未规定的搜索功能。 |
| U04 详情与通信 | 概况/收件箱/用量、多个作业、群及黑板 | 内容完整可读；正文/摘要展开不改变Agent读状态；消息排序、优先级、已读样式、群来源、黑板更正及解散标志准确。关闭详情回到画布并恢复焦点。 |
| U05 原生成员观察 | 加载、切换成员、工具展开、增量跟随、查看旧历史、关闭 | 身份和实际会话一致；底部跟随、历史滚动保持和新内容提示正确；只读且无发送/编辑/分叉入口。关闭仅释放观察引用，成员继续工作；成员终止后仍可读完整工具输入输出。 |
| U06 状态与停止 | 运行、等待、空闲、终止结果、清理及告警 | 同一含义在卡片、详情、列表和下拉中一致；清理不遮蔽结果。已提交/完成/失败反馈区分，范围和按钮文案正确，断线禁用；未真实触发的状态明确记未观察。 |
| U07 插件设置 | 分组、角色职责/预设/技能/模型与参数、继承与覆盖、输入草稿、保存和冲突 | 按设计逐项核对配置能力，当前入口缺项也记为界面差距；混合模型业务可通过模式配置继续验证。跨分组保留未保存内容；清空覆盖恢复继承；非法数字/JSON给出提示且保留草稿；两窗口制造真实修订冲突，比较本地与最新值后再保存。新运行、后续准入和重启生效的提示准确。 |
| U08 用量与阅读体验 | 自身/分支用量、混合模型、长任务、错误和长中文 | 按真实调用对账，不重复累加流式累计值；缺失数据用“—/不可用”。服务额度与金额不是同一指标，无可靠费率时不显示零费用。长文本不遮挡按钮，重要信息能通过聚焦/展开读全。 |

独立Web执行共享画布、详情、连接和停止检查；宿主导航、原生阅读器和设置在DSH Web与Desktop执行。独立Web不具备的宿主入口记“不适用”，不计为失败。

### 外观检查规格

以[界面元素](../design/design.md#界面元素设计)、[交互](../design/design.md#界面交互设计)、[DSH宿主界面](../design/design.md#dsh-宿主界面设计)及其SVG/动效示例作为参考。

- **宽度与主题**：常规桌面、紧凑桌面、390px窄窗口；另精确测量实际画布宽度559/560/561 CSS px。原生面板跟随宿主主题，独立Web跟随系统主题，均测试浅/深色及减少动态效果。
- **几何与层级**：按未缩放布局坐标或换算回100%比例测量。宽屏卡片216px、圆角8px，宽屏根与首层40px；深层缩进32px、普通相邻卡片基准间距12px；身份13px、模型11px；群框留白24px、与非成员间隔至少8px，群框所需空间可扩展分支间距。测量记录缩放与DPR，窄屏卡片按设计适配。
- **一致性与可读性**：模型/厂商Logo、状态色、选中和聚焦样式一致；文字、数值、图标与按钮不碰撞。画布可按设计横向浏览，页面外壳不因溢出丢失控件；长内容能取得全文。
- **键盘与窄屏**：方向键、Home/End、Tab、Enter/Space、Escape及页签操作；覆盖详情的焦点约束和关闭返回；菜单、观察侧栏关闭后恢复原入口。触控/按钮区域按设计检查，重要操作不只依赖悬停。
- **动态过程**：新节点、连续折叠重开、真实实线/虚线消息、黑板写入和群框重排录屏；减少动态效果时直接切换，无残留退出卡片、错误线条或布局循环。视频结合事件时间核对设计时长，不只靠一张截图推断。
- **人工外观审阅**：按信息层级、留白、对齐、密度、状态辨识和连续操作稳定性逐项判断；问题给出实际截图、设计对照和具体修改建议，不只写“看起来不太好”。

## 7. 迭代实验、冻结验收与预算

### 两个调整方向

| 调整对象 | 可调整内容 | 约束与归因 |
| --- | --- | --- |
| 任务复杂度及自然需求 | 独立事项、领域跨度、依赖/冲突、材料长度、更新节奏、业务约束、自然需求的清晰度和表述 | 保持真实业务意义及独立可验答案；用户输入不加入角色、人数、模式ID或工具步骤。调整后是新任务版本，旧失败仍保留。 |
| skill与管理提示 | `agent-team`的需求理解/验收策略，`team-strategy`的模式发现/比较、规模管理、通信、派生与事件决策，pattern的适用描述和管理指引 | 允许完善设计要求的前置条件和接口用法；规则应适用于一类业务。不得按测试ID、特征短语或答案绑定模板和固定人数，也不注入本次预排的调用脚本。 |

`agent-team`侧重点是理解用户、复用/创建团队、交付任务及验收；`team-strategy`侧重点是判断组织形式、继续拆分、群协作、上下文延续及事件处理。模式指引提供其专有管理经验。一次修改先说明失败证据、待验证假设和预期改善的能力，避免为单个成功样本无限堆提示。 迭代不改变design规定的机制语义，不通过重命名模板、隐藏正常候选或删减正常可用工具来强迫唯一选择。

每轮使用版本元组：产品提交/包、skill及模式指引哈希、用户提示词版本、材料/难度版本、环境配置、观察边界。实际服务信息只入私有记录。相同skill版本通过正式安装加载到全新运行；不在旧Run里热替换来源导致快照或资源身份混杂。需要验证复用/恢复时，在该轮固定版本内部保留相应状态。

### 从探索到最终验收

| 阶段 | 操作 | 产出与判定 |
| --- | --- | --- |
| T0 建立基线 | 冻结当前正式skill与实现，校准干净环境，以N基础场景和M/G初始任务取得第一轮数据。 | 保留未经优化的输入、组织、路径、失败和覆盖矩阵；配置缺口与自主决策问题分开记录。 |
| T1 定位未覆盖原因 | 逐项判断未识别协作需要、模式不可发现/描述不足、选择错误、参数/执行错误、事件停滞或验收不足。必要时调用X辅助。 | 每个缺口有证据与可检验假设，不把所有失败笼统归为模型能力。 |
| T2 单轴迭代 | 优先只改任务复杂度/表达或只改skill策略，保持其他版本不变；在全新运行复测。 | 区分任务设计不足和指导不足。需要分析相互作用时，再做旧/新任务×旧/新skill的对照。 |
| T3 收敛与反例 | 对有效策略运行同类新材料，并重跑N01/N02/N06等简单任务及不适用模式反例。 | 目标模式能自主形成，同时不把简单需求过度组织成大团队，不机械套用每个模板；旧能力无实质退化。 |
| T4 冻结最终候选 | 固定统一的skill/管理指引及产品包，冻结覆盖判据、任务族版本和观察边界；待采用的产品或skill改动按PR评审。 | 最终验收使用同一正式候选版本；若合并后包身份变化，在实际交付包上确认。不能拼接互不兼容版本的成功。 |
| T5 留出材料验收 | 用未参与调优的新材料、同类新业务以及自然表述变体复测N/M/G、规模和UI。 | 必达单元有独立通过证据；skill变化后重新核对受影响单元和全局简单任务回归，最终表仅引用统一版本的证据。 |
| T6 交付与诊断归档 | 汇总首轮、探索轮及冻结轮的完整结果，附UI对照和X辅助结果。 | 说明改善来源、仍存限制、回归和用量；尚未覆盖的必达项保持未完成。 |

探索集可反复调整；留出材料的答案与正文不进入提示词或skill作者的调优上下文，由独立准备/评分步骤保管。留出验收失败后需要继续优化时，该材料转入探索记录，下一次正式验收使用新的留出材料，旧失败仍保留。普通业务材料可以呈现完整完成条件，不向Agent泄漏隐藏的标准答案、目标模板选择或评分路径。

建议冻结验收前，为每个必达单元预先登记3次独立验证运行，覆盖至少两份不同材料，其中包含留出材料；三次都需无编排救援、实际达到目标且业务通过。同一次完整运行可支持多个实际发生的目标，但不能把同一记录重复当作三次。任一次失败则该批未达标，保留全部结果，诊断后再安排新一批；不得从更多尝试中挑选三次成功。涉及版本调整时重新冻结，全部必达单元须由新版本的有效记录覆盖。报告每批和所有尝试的成功率；这里的次数是本轮验收建议，不是对模型普遍稳定性的保证。

### 等待边界与资源安排

接入校准后、各轮开始前，在私有记录中固定最长观察时间和无进展窗口。有效进展以相关产物、作业状态或实际处理判断，重复查询和心跳不算推进；在途请求和正常业务等待单列。运行停滞或观察上限到达时保留现场，不在同一运行里临场催促到成功。新的引导必须以新版本、新一次试验记录。

预算、调用上限和实际服务额度仅存本地私有记录。按基线实测分别安排探索、规模验证、冻结留出和辅助诊断资源，预留最终验收用量。若剩余额度不足，暂停扩大迭代并报告覆盖缺口及完成它所需的估算；不自动突破原约定预算，也不降低目标后宣称整体完成。辅助测试不能挤掉最终自主验证。

## 8. 取证、归因与交付

每次运行保存以下证据；原始记录留在本地，公开副本按第2节脱敏：

- 原始skill调用与业务输入、业务澄清及用户操作时间线；区分正常跟进和人工编排提示，标明基线/探索/冻结/留出/辅助来源。
- 产品包、skill及管理指引、提示词、材料难度的版本与差异；每次调整的假设、失败证据、对照结果和回归情况。
- 正式skill实际加载、环境/材料版本、私有模型配置及用量；不以文本回显代替skill被使用的证据。
- 会话、Run、Agent、作业、模式候选与实际选择、消息、群、事件和结果之间的关联。
- 需求覆盖清单、正式结果、主会话读回及验收动作、代码/文件差异和独立检查器输出。
- 用户变化或运行事件发生时间、Agent随后真实动作、停滞/循环/错误及收尾状态。
- 宿主与浏览器日志、原始截图和录像、实际规模、并发、交互延迟及关闭后的资源回收。

对自然执行没有采用的目标，当前轮记录“未覆盖”，随后按第7节继续迭代；缺少观察记录则记“证据不足”，都不能结束对应必达项。不要为了取得某项通过而回灌隐藏答案或替Agent完成下一步。故障归因区分技能入口、主会话的规划与验收、团队内部协作、插件契约、宿主和上游服务，用户体验失败仍在总表保留，不因归因为模型问题就从分母移除。
