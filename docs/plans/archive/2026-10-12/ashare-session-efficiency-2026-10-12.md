## 结论

本次团队的主要瓶颈是执行契约与管理流程。分配接口接受无法按预期执行的写入范围，Worker 运行后才发现无法写文件或调用 shell；总协调接管 shell 又与活动 Worker 的写入隔离冲突。错误随后被转成低信息通知，唤醒管理角色继续查询、试探和修复协议。大量成本花在处理框架自身的阻断，而非复盘业务。

Auditor 已移除；当前团队只有总协调、资源协调和两名 Worker。这些事件来自现存执行与调度路径。总协调确实已获得完整业务能力，问题是“拥有能力”和“此刻能够取得执行所需的写入许可”没有衔接好。

本次多 Agent 路径未交付正式验收通过的结果，15 分钟到期后受阻。最终报告随后由主会话接管采集、写作和检查。这个实际回退过程支持用户对本次低效率的观察，但不是同条件的单 Agent 对照实验，不能据此给出通用提速倍数。

本文整理诊断与后续方案；没有修改生产代码、配置或运行数据，也没有向任务发送指令或取消、恢复团队。

## 问题清单

### P0-1：写入范围在授权、互斥和执行阶段没有统一语义

实际分配为 `raw_2026-10-12/**` 和 `raw_2026-10-12/news/**`。授权入口接受这两个字符串，规范化和使用阶段却把 `**` 当作普通目录名。9 次 Worker write/edit 拒绝中，7 次属于预期授权目录内误拒，2 次是越界探测，后者被正确拦截。

相同输入调用生产函数，`raw/**` 不能写 `raw/_probe.txt`；改为 `raw` 目录即可写入。但是父范围 `raw/**` 与子范围 `raw/news/**` 的重叠检查也返回 false。仅修复写工具的 glob 匹配会引入并发写入冲突。

**解决：**明确只接受文件/目录路径，目录自然包含后代；对不支持的 glob 在分配前拒绝并给有效写法。授权校验、规范化、锁重叠检查、工具执行共用同一语义。若选择支持有限模式，必须一次完成上述全部环节。保留符号链接、越界和父子目录互斥检查。

**位置：**[protocol.ts](../../../../packages/dsh-flow/src/core/protocol.ts) 的 `validateWriteScope/scopesOverlap`；[scope.ts](../../../../packages/dsh-flow/src/core/scope.ts) 的 `canonicalScopeEntry/checkWriteAccess`；[actions.ts](../../../../packages/dsh-flow/src/core/actions.ts) 的分配预检与 `assertWriteScopeFree`。

### P0-2：能力分配成功不代表任务可执行

两名 Worker 已实际获得 shell/web_fetch，不能简单归因为没有授予 shell。执行层仍要求 bash/job_kill 的分配独占整个 workspace；子目录分配无法执行任何 bash，改 `workdir` 或只执行 `pwd` 也无效。本次因此出现 4 次 Worker bash 拒绝。

**解决：**在创建或分配前核对“任务需要的操作 × 实际能力 × 可执行写入范围”。返回有效能力及不可用原因，禁止将必需 shell 的任务分配成不可执行组合。在当前宿主隔离能力下，shell 任务采用整工作区独占、串行执行；web_fetch/read/定点 write/edit 可使用互不重叠目录。后续需要并行 shell 时，使用 DSH 真正执行的分配级文件隔离，不能靠模型自报只读或解析命令字符串替代沙箱。

**位置：**`scope.ts:118`、`actions.ts:527`、[role-tools.ts](../../../../packages/dsh-flow/src/core/role-tools.ts) 的 allocation 参数描述。

### P0-3：总协调具有完整权限，仍缺少可靠的接管流程

总协调 9 次 bash 被 `WRITE_CONFLICT` 拦住，因为 bash 的临时写 claim 覆盖整个 workspace，与正在执行的 Worker 相交。最后一次冲突发生在新闻 Worker 回合结束前；冻结时该 Worker 已无租约，不能把它诊断为陈旧锁泄漏。

**解决：**把接管做成明确的排空流程：禁止新工作进入 → 通知或中断原生执行 → 等待回合/工具副作用真正结算 → 释放分配 → 总协调取得执行许可。等待时返回可观察条件，不让模型反复执行注定失败的命令。验收中的文件读取继续使用读工具；需要独立重算时明确安排安全执行时机。若引入只读 shell，必须由 DSH 强制只读后才可降低其锁粒度。

**位置：**`cluster.ts:5355,5465`；`actions.ts:635`。不应提前释放仍在执行的写隔离来加速。

### P1-4：停止、收到、执行结束被混为一件事

总协调发送“停止”是普通协作消息，只有发送成功，不等于 Worker 收到。Flow 的同伴消息在回合起始收集；行情 Worker 的中途停止令仍为 PENDING，新闻 Worker 后两次停止令也未进入该回合原生日志。新闻回合起始还同时收到总协调“停止”和资源协调“继续落盘”的冲突指令。

**解决：**普通交流与控制分开。提供具有明确状态、收据和失败原因的 drain/cancel 路径，调用 DSH 的原生执行控制并等待终结事件。需要中途补充信息时，通过宿主支持的 next-step steering 投递并确认 receipt；普通消息不能承诺中断。业务指令由总协调唯一负责，资源协调不得独立重写交付要求。

**位置：**`cluster.ts:2717,2831`、[communication.ts](../../../../packages/dsh-flow/src/core/communication.ts) 的消息入库/通知；`actions.ts:635`。

### P1-5：确定性错误形成模型唤醒反馈循环

每次拒写同时通知两个管理者，包括错误发起者自身；`write-refused` 被列为 critical wake。已有 coalescing 仅合并尚未消费的同 key 通知，消费后再次失败会重新唤醒。实际进入模型上下文的通知只有“收到系统通知。”，模型再查询、尝试操作，又产生下一次拒绝。

**解决：**按错误指纹和关联分配归并到一个基础设施 blocker，状态没有变化时累计次数而不再次启动模型。发起者已有工具错误时，避免给它另发同一错误通知；只唤醒确有可执行动作的责任角色。通知包含错误代码、对象、有效授权、等待条件和合法下一步。保留全部审计事件，减少模型输入与 UI 逐条刷屏，两者分别处理。

**位置：**`cluster.ts:5484` 的 `#recordWriteRefusal`、critical subject 集合、`notifyInternal`、通知格式化与角色待办选择。

### P1-6：工具参数依赖长文本说明，模型反复修复协议

52 次目标调用错误中，17 次属于参数/投影/正式契约问题：字段选错、缺 transaction_id/issue_id、父约束未继承、责任映射缺失、标准文字改写、错误收件人字段及 resolution evidence 错形。`params` 是不透明 JSON，部分 action 的合法字段没有完整说明，Allocator 的 resolve_issue 甚至缺少参数说明。

**解决：**按 action 提供结构 schema，明确 required、enum、字段路径及合法最小实例；查询公开对象类型和字段闭集。默认继承父约束，引用标准和计划时由框架展开规范原文，减少模型重复抄录；不能放宽正式标准、证据检查或让框架替模型宣称业务通过。错误返回最小修复差异及当前合法动作，保留命令幂等和原子回滚。

**位置：**`role-tools.ts:94,160`、[briefing.ts](../../../../packages/dsh-flow/src/core/briefing.ts)、[contracts.ts](../../../../packages/dsh-flow/src/core/contracts.ts)、`actions.ts:844,866,1073,2150`。

### P1-7：基础设施阻断被走成业务交付与返工

两名 Worker 最终提交的是“无法落盘”的阻断说明。总协调正确拒绝了行情交付，未出现假接受；但是权限问题随后进入 validate、issue、resolve_issue 等业务恢复动作。一次基础设施问题因此又消耗业务验收、返工和资源调整回合。

**解决：**区分业务不合格、工具参数错误、基础设施阻断和需要用户输入。确定性基础设施失败使用结构化 blocker，不作为成功业务产物提交；恢复授权后续用同一业务计划，不能因权限故障改写验收标准。修复前重复同类探测应停止；基础设施恢复由确定性状态机处理，不依赖多名模型互相劝说。

### P1-8：缺省管理结构的成本过高，资源协调没有必要每次依赖模型

一个管理域的两名管理者消耗 114 次调用和 69 条模型回复；其中资源协调 52 次调用。初次拆分近 4 分钟反复修复协议，首名 Worker 到第 5 分钟才开始业务执行。

**解决：**以“一个执行者足够则直接执行”为缺省。保留总协调的业务规划与验收，把常规分配、排队、额度结算、排空后的回收做成确定性操作。资源协调 Agent 按复杂资源决策需要启用，评估减少其模型回合；先修契约，再用同条件实验判断是否应移除固定 Allocator。不能仅凭本次占比宣称删掉它一定加速。

### P1-9：并发指标描述不清，长回合包含工具等待

新闻 Worker 排队 108 秒。调度许可包住完整 runTurn，并等待 `live.whenIdle`；工具 I/O、长错误说明和多轮协议修复都在许可区间内。这不是每次模型请求的实际并发。

**解决：**区分身份数、活动回合数、调度许可、排队时间和宿主实际请求观测。为已有业务工作提供公平排队，避免没有可行动事件的管理回合抢占资源。长回合采用宿主支持的让出/中断边界；若需请求级公平，由 DSH 提供。遵守 ADR 0003，Flow 不重新挂载模型请求中间件或引入 Token 硬预算。

**位置：**`cluster.ts:2712,2830`、[runtime.ts](../../../../packages/dsh-flow/src/core/runtime.ts) 的原生 Agent 完成等待；[ADR 0003](../../../adr/0003-use-host-model-capacity-and-compaction.md)。

### P1-10：模型看到的工具、权限上下文与实际执行条件不一致

两次未授权 browser 调用被正确拒绝；主会话的 web_search 缺独立凭据。成员 runtime-context 告知 DSH workspace 可写，没有在同层解释 Flow 的窄分配及 bash 限制。主会话还携带 17,021 字符的完整 skill 目录；四名成员没有重复注入这份目录，不能将其误计为四份。

**解决：**可见工具清单与有效能力一致，移除没有配置的提供方或明确其不可用原因。将 DSH 与 Flow 约束合成一次有效授权说明，展示实际可写目录、shell 条件和不可用工具。按任务检索相关 skill，裁剪无关编码/GUI 说明；不要通过扩大 Allocator 权限来消除其业务浏览器报错。

### P1-11：回退、终态通知与交付归属没有清晰衔接

截止通知唤醒主会话后，主会话接管生成报告，随后自身调用取消和回收。终态通知又带着整段 objective 注入主会话；其交付回合结束后立即出现第 3 回合，补充快照已有 2 次状态/文件调用。这是终态事件继续消耗模型的实例。团队仍没有接受最终报告，用户看到的文件交付与团队状态不一致。

**解决：**明确团队失败后的回退负责人和交付状态。终态回执应简短，只包含状态变化、失败原因、产物引用及待处理动作；由本会话刚发起的收尾操作不再引发一轮独立模型工作。展示“团队未完成、主会话接管交付”，不能把文件存在自动标成团队验收成功。

### P1-12：停滞保护把交流和其他成员事件也算成本角色进展

当前 16 个完成回合全部记为 `progress=true`。进展判断使用全 cluster 事件序号；消息发送、投递、确认和其他成员的事件都可能重置管理者停滞计数。资源协调第 6 回合的两次分配均失败，仍因期间的通信事件记为有进展，不能及时识别同一阻断上的循环。

**解决：**按本角色负责的 transaction/incident 追踪可核查状态变化，将有效业务/资源推进、等待依赖、重复失败分开。合法协作仍保留，但相同阻塞的反复转述不能无限重置恢复计数；其他成员推进不能替本角色掩盖无进展。

**位置：**`cluster.ts:2902,5746` 与进展事件分类。

### P2-13：数据与产出证据没有形成可复用输入，验收测试未覆盖真实故障链

已有 8 条 HTTP 200 回执，说明网络并非全面不可用；但在冻结窗口没形成稳定 raw/manifest。后续主会话的脚本才开始批量采集。有限检查发现新浪分页响应被解析合并而非逐页原样保留，page 37 记录 empty/unparsable；5,572 条记录不能自动证明全市场覆盖完整。

**解决：**一次采集并保存原始响应、URL、HTTP 状态、时间、哈希和覆盖/失败清单，后续分析共享同一冻结输入。大内容通过文件引用交接，通知只传摘要和证据引用。新增原生集成覆盖“规划→分配→真实 HTTP→文件归档→提交→总协调重算验收”，并加入权限拒绝、在途停止、重叠写入和终态通知故障场景。纯算术回环、包构建及单元测试不能代替这条验证链。

## 实施顺序与验收

### 第一批：修复执行契约与失败恢复

1. 统一 write_scope 语义，提前拒绝无效模式并检查重叠；补全 shell 分配预检与有效能力返回。
2. 为当前宿主选择可执行形态：一个独占根目录的采集者；并行 HTTP/read/定点写任务使用明确互斥目录；任意 shell 并行等待宿主隔离能力。
3. 实现 drain/cancel 收据与安全结算流程，禁止活动执行期间直接释放写入隔离。
4. 用结构化基础设施 blocker 阻止权限错误重复试探及业务验收绕路。

**验收：**无效分配不创建运行成员；授权目录内写入、越界拦截、父子重叠检查一致；活动写入未结算前锁不释放；停止成功必须有真实投递/终结证据；同一错误且状态不变时不再重复启动恢复回合。

### 第二批：缩短管理路径和通知链

1. 按 action/query 补全 schema、字段枚举、继承和引用规则、可操作错误。
2. 通知按责任与可行动性路由；消费后的重复故障继续归并；终态收尾不再次唤醒已交付主会话。
3. 常规资源操作改为确定性管理，资源协调 Agent 按需启用；合并重复状态查询；按角色及阻断对象识别真正进展。
4. 展示排队、业务产物、协议错误和基础设施阻断；默认截止时间在启动时明确可见，复杂任务按实际需求配置。不能只延长时间来掩盖循环。

**验收：**合法业务路径无需反复猜参数；失败回执给出对象和下一动作；重复低信息通知不产生多轮模型工作；读权限说明与实际策略一致；业务验收和权限、幂等保护继续有效。

### 第三批：做真实效率对照，再决定结构裁剪

对照三种执行形态：单 Agent、总协调＋Workers、总协调＋Allocator＋Workers。固定同一模型/推理设置、数据快照、工具授权、任务与验收条件，区分冷缓存/热缓存，记录失败样本，不选择性重跑。

记录正确交付率、首次有效产出时间、端到端时长、业务/控制调用数、工具错误分类、非缓存输入/缓存/输出、排队时间和基础设施恢复次数。简单任务应优先避免固定管理层；对可并行任务只有在同等质量下出现稳定收益才扩大团队。对常规资源协调使用 `reasoning=max` 是否必要，同样通过独立对照判断，不另加 Flow 输出截顶。

当前证据不足以给定通用速度目标。第一批首先要求真实端到端交付成功，再对固定样本制定性能门槛。
